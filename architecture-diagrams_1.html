Architecture Reference

Payment Processing System

One generic payment API, per-method processing via a Strategy/Provider pattern, wired through Spring's dependency injection so new payment methods register themselves with zero changes to existing code.

02

Class diagram

PaymentProcessor is the strategy interface. AbstractPaymentProcessor is a generic Template Method base class — it owns the five-step orchestration once; each concrete processor only fills in the steps. 

classDiagram
  class PaymentProcessor {
    <>
    +getMethodType() String
    +process(JsonNode raw) PaymentResult
  }

  class AbstractPaymentProcessor~TRequest, TGatewayReq, TGatewayResp~ {
    <>
    #ObjectMapper objectMapper
    +process(JsonNode raw) PaymentResult
    #parseRequest(JsonNode raw) TRequest*
    #validate(TRequest req)*
    #toGatewayRequest(TRequest req) TGatewayReq*
    #callGateway(TGatewayReq req) TGatewayResp*
    #toPaymentResult(TGatewayResp resp) PaymentResult*
  }

  class CardPaymentProcessor {
    +TYPE : String = "CARD"
    -CardGatewayClient gatewayClient
    -Validator validator
  }

  class PaypalPaymentProcessor {
    +TYPE : String = "PAYPAL"
    -PaypalGatewayClient gatewayClient
    -Validator validator
  }

  class PaymentProcessorRegistry {
    -Map~String, PaymentProcessor~ processorsByType
    +resolve(String methodType) PaymentProcessor
    +isSupported(String methodType) bool
    +getSupportedMethods() Set~String~
  }

  class PaymentMethodContext {
    <>
    +set(String methodType)
    +get() String
    +clear()
  }

  class PaymentMethodHeaderFilter {
    -PaymentProcessorRegistry registry
    +doFilterInternal(req, res, chain)
  }

  class PaymentController {
    -PaymentProcessorRegistry registry
    +processPayment(JsonNode payload) PaymentResult
  }

  class PaymentMethodConfigController {
    +supportedMethods() Set~String~
    +fields(String method) List~FieldDefinition~
  }

  class PaymentMethodFieldConfigService {
    -Map~String, List~FieldDefinition~~ cache
    +getFields(String methodType) List~FieldDefinition~
  }

  class FieldDefinition {
    +String name
    +String label
    +String type
    +bool required
    +String pattern
    +List~String~ options
  }

  class CardGatewayClient { +charge(CardGatewayRequest) CardGatewayResponse }
  class PaypalGatewayClient { +capture(PaypalGatewayRequest) PaypalGatewayResponse }
  class PaymentResult { +String transactionId +PaymentStatus status +String message }

  PaymentProcessor <|.. AbstractPaymentProcessor
  AbstractPaymentProcessor <|-- CardPaymentProcessor
  AbstractPaymentProcessor <|-- PaypalPaymentProcessor
  PaymentProcessorRegistry o-- "many" PaymentProcessor : auto-collected by Spring
  PaymentController --> PaymentProcessorRegistry
  PaymentController --> PaymentMethodContext : reads
  PaymentMethodHeaderFilter --> PaymentProcessorRegistry
  PaymentMethodHeaderFilter --> PaymentMethodContext : writes
  CardPaymentProcessor --> CardGatewayClient
  PaypalPaymentProcessor --> PaypalGatewayClient
  AbstractPaymentProcessor ..> PaymentResult : produces
  PaymentMethodConfigController --> PaymentProcessorRegistry
  PaymentMethodConfigController --> PaymentMethodFieldConfigService
  PaymentMethodFieldConfigService --> FieldDefinition : loads
Note the direction of the registry arrow: PaymentProcessorRegistry depends on the interface, and Spring injects List<PaymentProcessor> — every @Component implementing it joins the map automatically, so this diagram doesn't change shape when a method is added, only gains another leaf under AbstractPaymentProcessor.
03

Request sequence — happy path

A single CARD payment from click to response. PAYPAL (or any future method) follows the identical shape, just swapping the last three participants. 

sequenceDiagram
  autonumber
  participant UI as React UI
  participant F as PaymentMethodHeaderFilter
  participant C as PaymentController
  participant R as PaymentProcessorRegistry
  participant P as CardPaymentProcessor
  participant V as Validator
  participant GC as CardGatewayClient
  participant EXT as Card Gateway (external)

  UI->>F: POST /api/payments\nheader X-Payment-Method: CARD\nbody {cardToken, amount, ...}
  F->>R: isSupported("CARD")?
  R-->>F: true
  F->>F: PaymentMethodContext.set("CARD")
  F->>C: chain.doFilter()
  C->>R: resolve("CARD")
  R-->>C: CardPaymentProcessor instance
  C->>P: process(rawPayload)
  P->>P: parseRequest(raw) → CardPaymentRequest
  P->>V: validate(request)
  V-->>P: ok (or throws InvalidPaymentPayloadException)
  P->>P: toGatewayRequest(request) → CardGatewayRequest
  P->>GC: charge(gatewayRequest)
  GC->>EXT: (real integration point)
  EXT-->>GC: gateway response
  GC-->>P: CardGatewayResponse
  P->>P: toPaymentResult(response) → PaymentResult
  P-->>C: PaymentResult
  C-->>UI: 200 OK {transactionId, status, message}
  F->>F: PaymentMethodContext.clear() (finally block)
04

Filter validation logic

The one place that understands "the method identifier lives in a header." Everything downstream can assume the method is already valid. 

flowchart TD
  A["Incoming request"] --> B{"Is it POST /api/payments?"}
  B -- No --> Z1["Pass through untouched"]
  B -- Yes --> C{"X-Payment-Method\nheader present?"}
  C -- No --> D["400 MISSING_HEADER"]
  C -- Yes --> E{"registry.isSupported(method)?"}
  E -- No --> F["400 UNSUPPORTED_PAYMENT_METHOD"]
  E -- Yes --> G["PaymentMethodContext.set(method)"]
  G --> H["chain.doFilter() → Controller"]
  H --> I["finally: PaymentMethodContext.clear()"]

  classDef ok fill:#EDF0FC,stroke:#3454D1,color:#14171A;
  class D,F err;
  class G,H,I ok;

06

Data-driven UI flow

The React form never hard-codes a field name — it renders whatever the backend's field-config says exists for the selected method. 

flowchart TD
  A["App loads"] --> B["GET /api/payment-methods"]
  B --> C["Populate method dropdown\n(e.g. CARD, PAYPAL)"]
  C --> D["User selects a method"]
  D --> E["GET /api/payment-methods/{method}/fields"]
  E --> F["Render inputs generically\nfrom FieldDefinition list\n(text / number / select)"]
  F --> G["User fills form, clicks Pay"]
  G --> H["POST /api/payments\nheader: X-Payment-Method\nbody: collected field values"]
  H --> I{"2xx?"}
  I -- Yes --> J["Show transactionId + status"]
  I -- No --> K["Show error message + message field"]
